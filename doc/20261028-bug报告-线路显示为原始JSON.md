# Bug 诊断报告：库存卡片"线路"显示为原始 JSON

- **日期**：2026-10-28
- **状态**：已修复（normalize.rs 已改，等下一轮采集数据自愈）
- **严重级别**：P3 轻微（显示层问题，不影响监控/告警功能）
- **报告人**：Claude Agent（Bug Diagnosis Skill）

---

## 问题描述

库存卡片"线路"字段显示为原始 JSON 字符串，如：

```
线路: {"cm":"CMI","ct":"163","cu":"4837"}
```

正常应显示为人类可读的线路文本（如 `CMI+163+4837`）。

## 环境信息

- 分支/版本：main（v0.3.5 之后工作区）
- 相关模块：`src-tauri/src/monitor/normalize.rs`（数据归一化）、`src-tauri/src/provider/kyoa.rs`（上游拉取）、`src/components/ProductCard.tsx`（前端渲染）
- 数据源：`https://kyoa.de/data.js`
- 复现步骤：应用正常轮询后，凡上游 route 为对象形态的商品，卡片即显示 JSON 原文

---

## 结论（先说答案）

**根因是上游 kyoa.de 的 data.js 数据格式变更**：部分商品的 `route` 字段从纯文本字符串（如 `"9929+CMIN2"`）改成了结构化对象（如 `{"ct":"163","cu":"4837","cm":"CMI"}`，即电信/联通/移动三网回程线路）。而本项目 `normalize.rs` 的通用取文本函数 `text()` 对非字符串值的兜底行为是 `serde_json::Value::to_string()`——对对象就是输出 JSON 原文。该原文一路入库、传到前端、被 `ProductCard` 原样渲染，即用户看到的现象。

**不是**本次代码改动引入的回归——应用代码没有任何变化，是上游数据契约单方面变了。

---

## 可能原因分析（诊断过程）

| # | 原因 | 概率 | 结论 |
|---|------|------|------|
| 1 | 上游 data.js 的 route 字段改为对象形态，`text()` 兜底 `to_string()` 把 JSON 原文当文本 | 高 | ✅ 已确认 |
| 2 | 前端渲染逻辑改动引入 | 低 | 排除：`ProductCard.tsx:160` 一直就是直接渲染字符串值 |
| 3 | 本地 DB 被污染/残留 | 低 | 排除：源头就是上游数据，且每次轮询都会重写（见"自愈能力"） |

### 关键证据（上游真实数据统计，2026-10-28 拉取）

对 `https://kyoa.de/data.js` 全量 2131 个商品统计 route 字段形态：

| 形态 | 数量 | 样例 |
|------|------|------|
| 字符串（原有形态） | 1882 | `""`、`"9929+CMIN2"`、`"CN2GIA+9929+CMIN2"`、`"电信 CN2 GIA / 联通 9929 / 移动 CMIN2"` |
| 对象 `{ct,cu,cm}` | 180 | `{"ct":"CN2GIA","cu":"9929","cm":"CMIN2"}`、`{"ct":"163","cu":"4837","cm":"CMI"}` |
| 对象 `{single}` | 36 | `{"single":"普通直连"}`、`{"single":"直连优化"}` |
| 空对象 `{}` | 33 | `{}` |

`ct/cu/cm` 值域（线路代号）：`163、4837、CN2、CN2GIA、CTGGIA、9929、CMI、CMIN2、IIJ、Softbank`。其中 ct=电信回程、cu=联通回程、cm=移动回程。

用户截图中的 `{"cm":"CMI","ct":"163","cu":"4837"}` 正是 `{ct,cu,cm}` 对象形态之一。

## 调用链与依赖分析

```
kyoa.de/data.js（上游，route 已部分改为对象形态）
  → KyoaProvider::fetch / parse_payload            [src-tauri/src/provider/kyoa.rs:36,143]
  → normalize(data)                                 [src-tauri/src/monitor/normalize.rs:109]
      route: text(product.get("route"))             [normalize.rs:197]
      text(): 非字符串 → other.to_string()          [normalize.rs:63-71]  ← 缺陷点
  → engine.rs 每轮采集对存量商品无条件 update_product [src-tauri/src/monitor/engine.rs:450]
  → SQLite products.route 存入 JSON 原文            [src-tauri/src/store/catalog.rs:112-143]
  → 前端 ProductView.route → <Tag>渲染               [src/components/ProductCard.tsx:160]  ← 现象点
```

`text()` 的实现（`normalize.rs:63-71`）：

```rust
fn text(value: &serde_json::Value) -> String {
    match value {
        serde_json::Value::Null => String::new(),
        v => match v {
            serde_json::Value::String(s) => s.clone(),
            other => other.to_string(),   // ← 对象在此变成 JSON 原文
        },
    }
}
```

**自愈能力**：`engine.rs:450` 对每个已存在商品每次轮询都调用 `update_product`，其中 route 无条件刷新（`catalog.rs:116`）。因此只要在 normalize 层把对象转成可读文本，**下一轮采集后所有旧数据自动覆盖，无需数据迁移**。

### 受影响范围

- 库存卡片"线路" Tag（用户所见）
- 告警规则 `routeLike` 匹配（`store/rules.rs` + `catalog.rs:398` 的 `p.route LIKE ?`）：JSON 原文形态下用户填 `CMI` 恰好能撞上子串，但语义是错的；修复后按可读文本匹配，语义恢复
- 通知消息中如引用 route 的部分同上

## 修复建议（待确认后实施）

在 `normalize.rs` 中为 route 增加专用转换函数（不改通用 `text()`，避免影响其他字段）：

1. 字符串 → trim 后原样返回（兼容 1882 个存量形态）；
2. 对象含 `single` 键 → 返回其字符串值（如"普通直连"）；
3. 对象含 `ct/cu/cm` → 按 `ct+cu+cm` 顺序用 `+` 拼接（与上游既有字符串风格 `"CN2GIA+9929+CMIN2"` 一致）；三值相同则去重为单值；值为空串的键跳过；
4. 空对象 / 其他形态 → 空串；
5. 补齐 `normalize.rs` 单测：覆盖上述四种形态 + 三值去重场景。

预期效果：`{"cm":"CMI","ct":"163","cu":"4837"}` → 显示 `163+4837+CMI`；`{"ct":"CN2GIA","cu":"CN2GIA","cm":"CN2GIA"}` → 显示 `CN2GIA`；`{"single":"普通直连"}` → 显示 `普通直连`。

无需改前端、无需改 DB schema、无需数据迁移（下一轮采集自动覆盖）。

- `spec` 内部键带 emoji 前缀且两代键名混用（"💻 CPU"×2038 与 "CPU"×90；"🌐 IP地址" 与 "🌐 IP"；"IP属性/IP 属性/IP类型" 变体）：前端 `spec.ts` 的 KEY_RE 已剥 emoji 前缀，PRIORITY 兼容 IP地址/IP 同义键。
